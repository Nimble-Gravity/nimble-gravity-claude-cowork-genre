Use Cases by Industry

The quickest way to see what Cowork is worth is to point it at a job that matters in your own work. This lesson covers the tasks worth trying first in each industry, and the one Anthropic plugin approved at Gen Re that you can build on instead of starting from nothing.

Use Cowork · ~20 min
01 — Start where it pays off

Pick a job that ends in a deliverable

In every industry, the best first tasks are the multi-step, multi-file jobs you already do by hand. They produce a finished artifact, and you can tell at a glance whether it's right.

Research and synthesis

Hand Cowork a set of sources and ask for a structured brief with citations. It pulls the relevant points out of a stack of documents and gives you back something you can review.

Document and data prep

Pull source files into a draft, build a working Excel model, or turn a pile of contracts and reports into something clean you can actually read.

02 — By industry

Build on the approved Anthropic plugin

Anthropic publishes first-party skill and plugin packs for regulated work, all built so that the agent drafts and a person signs off. At Gen Re, exactly one has been approved for use: the Legal plugin. Seed your labs from it rather than from a blank page.

Approved at Gen Re

Legal — contract and treaty-wording work

The anthropics/claude-for-legal marketplace ships plugins such as /review-contract and /triage-nda. A cold-start interview writes a practice profile the other skills read, and the result is always a draft for a reviewer to sign off — the same shape as reviewing treaty and facultative wordings.

The draft-and-review pattern fits P&C, Life & Health, and claims.
Not approved

Every other pack goes through review first

Anthropic also publishes packs for financial services, life sciences, and general knowledge work — none of them are approved at Gen Re, so don't install them. If one maps onto your workflow, raise it through the governance process covered in Workshop 4 and let it clear review before anyone builds on it.

Approved today: the Legal plugin. Nothing else.
03 — See it on your own work

Run a starter against your files

A demo on sample data proves nothing about your job. Run a starter task on your own files and watch how the output reflects your context. That's the moment a curious user turns into a daily one.

01
Pick one job from your week
Something repetitive and heavy on documents. The more real it is, the sooner the value shows. For this Gen Re IT cohort, the two anchor use cases: documentation generation — turning a legacy Excel/VBA or R model into readable process documentation and a build-ready spec — and technical review — a second pair of eyes on code, flagging potential errors and improvements before human review. Also proven in your pilot: mapping client trade descriptions to internal categories, researching missing information from submissions, and prototyping a dashboard from a reporting pack. Every output is a draft the responsible engineer or analyst signs off on.

Proof from your own pilot

These aren't hypotheticals — Gen Re's pilot community has already done this work with Claude: IFRS 18 impact analysis in an hour instead of half a day, an expected-loss view from a 70-tab submission in minutes, treaty-and-amendment interpretation, claims-outlier analysis, a redesigned claim form in four minutes, and legacy Excel/VBA models translated into specs for the Python platform. 04 — Live demo · Tell → Show → Recap

Watch one run: a solution profile from a folder

The documentation use case, run live. A folder of legacy-system files goes in; a solution profile document with an architecture diagram comes out — a draft the responsible engineer signs off on. Download the same folder below and run it alongside the presenter.

1 · Tell

Frame it before you run it

"This is the workbook problem every IT team has: the author left, nobody knows what the factors do, and modernization starts with documenting what it does today. Cowork gets one folder — the macro export, the analysts' run notes, the workbook data snapshot, the factor export, the transcript of the author's handover call, and the modernization kickoff notes — and nothing else."

Name the deliverable before it exists: a solution profile plus an architecture diagram.
2 · Show

Delegate, then let the silence work

Paste the prompt, grant the folder, hit go. Narrate only what chat can't do: it reads all four files, cross-references the runbook against the code, and asks before it writes. When the drafts land, open the architecture diagram first — the picture is the fastest proof it understood the system.

Don't talk over it. Watching it work unprompted is the demo.
3 · Recap

Land the pattern, not the magic

Point at what the profile got right — and at what it flagged as an open question instead of inventing (the casualty discrepancy, the hand-maintained row count). Then hand it to the room: same folder, same prompt, your machine — and after that, a system you actually own.

Folder in → reviewable draft out → a person signs off. That's the whole pattern.
📁
The demo folder — download, unzip, grant

Download solution-profile-folder.zip, unzip it somewhere sensible, and grant Cowork that one folder. Inside — the files a real handover leaves behind: TreatyLayerPricer-macro-export.docx (the VBA as found), TreatyLayerPricer-data-snapshot.xlsx (the workbook's four tabs), quarterly-run-notes.docx (how the analysts actually run it), factors.csv (the factor export), handover-call-transcript.docx (the departed author's recorded call), and modernization-kickoff-notes.docx (what the team agreed to deliver). Fictional, and deliberately imperfect — the gaps are what make the open-questions section interesting.

Demo prompt 1 — the delegation 
Read everything in this folder. It documents a legacy Excel/VBA treaty-layer pricing tool: a Word export of the macro, the analysts' quarterly run notes, an Excel snapshot of the workbook's tabs, a factor export, the transcript of the original author's handover call, and the modernization kickoff meeting notes.

Write a solution profile document, saved as a Word document (solution-profile.docx) in this folder, that a new engineer or analyst could rely on:

1. Purpose and business context — what it prices and why it matters
2. Users, owner, and run cadence
3. How it runs today — the quarterly process step by step, including every manual step around the workbook
4. Inputs and data sources — everything the macro reads and where it comes from
5. Outputs and consumers — where the results go and who uses them
6. Dependencies and assumptions — hardcoded values, hand-maintained cells, single points of failure
7. Known risks and quirks — each with the file and line or cell it lives on
8. Open questions — anything the sources don't explain; do not invent answers

Create an architecture diagram of the as-is state and save it alongside the document as its own file the reviewer can open (an image or an HTML page): upstream sources, the workbook's tabs and macro, every manual step, and the downstream consumers. Reference it from the document.

Cite the file (and line or cell) for every claim. This is a draft for the responsible engineer to sign off on — not the final word.
Demo prompt 2 — the follow-up steer 
Two changes. In the architecture diagram, separate automated flows from manual ones — solid arrows for what the macro does, dashed arrows for what a person does by hand. Then add a "Modernization considerations" section: what the Python platform team should keep, fix, or confirm before porting. Keep everything else exactly as it is.

The follow-up is part of the demo: the first draft is never the end of the conversation, and steering with one precise message — instead of starting over — is the habit that separates delegation from chat.
